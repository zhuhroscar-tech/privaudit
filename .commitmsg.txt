fix: detect PipeWire node-id reuse across polls in diff_snapshots

diff_snapshots() keyed continuity purely on node_id: a node_id present in
both the previous and current snapshot was always treated as "still the
same ongoing capture, no event." PipeWire explicitly does not guarantee
node ids stay unique over time -- pw_map_remove() puts a freed id back on
a free list ("the id may get re-used in the future", pipewire/map.h), and
a real consumer (xdg-desktop-portal-wlr#381) hit exactly this: a torn-down
stream's node_id was immediately reassigned to an unrelated new stream.

If app A's capture node stops and app B's new capture node is assigned
the same recycled node_id before privaudit's next 2s poll, the old
node_id-only diff produced ZERO events -- silently dropping both the real
stop and the real start. For a mic/camera access-history tool, this is
the exact kind of gap the tool exists to prevent: a period of active
capture (by a different app than the log shows) with no recorded event
at all.

Fix: diff_snapshots() now checks pid (when available on both sides) and
capture kind (mic/camera) as evidence the same node_id is actually a
different session. A pid or kind mismatch on a shared node_id now emits
the correct stop+start pair instead of silent continuity. When neither
snapshot has a pid to compare, there's no reliable signal, so the
previous assume-continuity behavior is kept as a narrower, now-documented
limitation.

Reproduced first (0 events for a same-id/different-pid pair on the
pre-fix code), then fixed, then verified with 4 new regression tests --
2 of which were confirmed to fail against the reverted pre-fix code for
exactly this behavioral reason (git stash proof), not merely an
import/syntax failure. 65/65 tests pass; core.py stays at 100%
statement coverage with the new branch fully exercised.

Also corrected a stale claim in both READMEs (English + Simplified
Chinese) left over from the 0.1.5 pw-dump-failure fix: they still said
"failed pw-dump reads are treated as empty snapshots" when the actual
post-0.1.5 behavior is "treated as unknown, previous state carried
forward." Documented the new node-id-reuse handling and its pid-less
limitation in the same paragraph.

Bumped 0.1.5 -> 0.1.6 (user-visible correctness fix in watch's core
event-detection path).
